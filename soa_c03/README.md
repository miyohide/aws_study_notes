# これは何か

AWS Certified CloudOps Engineer - Associate(SOA-C03)取得のための個人的勉強用メモです。

試験ガイドは[AWS Certified CloudOps Engineer - Associate (SOA-C03)](https://docs.aws.amazon.com/ja_jp/aws-certification/latest/sysops-administrator-associate-03/sysops-administrator-associate-03.html)を参照。

# 試験の概要

CloudOps エンジニアを対象とし、AWS でのワークロードのデプロイ、管理、運用の能力を検証する試験。

- 合格スコア: 720（100〜1,000 の換算スコア）
- 採点対象の設問: 50 問（採点対象外が別途 15 問）
- 設問形式: 択一選択問題と複数選択問題

## コンテンツ分野と重み

| 分野 | 内容 | 重み |
| ---- | ---- | ---- |
| 分野 1 | モニタリング、ログ記録、分析、修復、パフォーマンスの最適化 | 22% |
| 分野 2 | 信頼性と事業の継続性 | 22% |
| 分野 3 | デプロイ、プロビジョニング、オートメーション | 22% |
| 分野 4 | セキュリティとコンプライアンス | 16% |

試験ガイドによる重み設定であり、各分野に出題が偏ることを把握しておく。分野 1〜3 の運用系が全体の 2/3 を占める。

# 分野 1: モニタリング、ログ記録、分析、修復、パフォーマンスの最適化

システムの状態を可視化し、異常を検知して自動修復するためのサービス群。

## Amazon CloudWatch

AWS リソースやアプリケーションのメトリクス、ログ、イベントを収集・可視化・監視するサービス。運用監視の中核。

- メトリクス: リソースのパフォーマンス指標を収集。カスタムメトリクスも送信可能
- アラーム: メトリクスがしきい値を超えたら通知やアクション（Auto Scaling、EC2 停止など）を実行
- ログ（CloudWatch Logs）: ログの収集・保存・検索。Logs Insights でクエリ分析が可能
- ダッシュボード: 複数メトリクスを一画面で可視化
- エージェント（CloudWatch Agent）: EC2 やオンプレのメモリ・ディスク使用率などの OS メトリクスとログを収集

### 基本モニタリングと詳細モニタリング

| 項目 | 基本モニタリング | 詳細モニタリング |
| ---- | ---------------- | ---------------- |
| メトリクス収集間隔 | 5 分 | 1 分 |
| 料金 | 無料 | 有料 |
| デフォルト | 有効 | 無効（オプションで有効化） |
| ユースケース | 粗い監視で十分な場合 | スパイク検知、オートスケーリング精度向上 |

### カスタムメトリクスと高解像度メトリクス

- カスタムメトリクス: `PutMetricData` API でアプリ独自の指標(例: キュー長、業務指標)を送信できる。メモリやディスク使用率など EC2 の OS 内部指標も標準では取得できないため、CloudWatch Agent 経由でカスタムメトリクスとして送信する
- 高解像度メトリクス: 標準は 60 秒粒度だが、1 秒または 10 秒粒度で送信できる。短時間のスパイク検知に有効（アラームも最短 10 秒で評価可能）
- メトリクスの保持期間: 粒度が細かいデータは一定期間後により粗い粒度へ集約されて保持される（高解像度・1 分データは短期、1 時間データは最大 15 か月）

### CloudWatch アラーム

メトリクスがしきい値を満たすと状態遷移し、アクションを実行する。

- 状態: `OK` / `ALARM` / `INSUFFICIENT_DATA`
- アクション: SNS 通知、Auto Scaling、EC2 アクション(停止/終了/再起動/復旧)、Systems Manager アクション
- 評価期間と データポイント: 「M 個中 N 個のデータポイントがしきい値超過で ALARM」のように設定できる
- 欠落データの扱い: `missing`(無視) / `notBreaching`(正常扱い) / `breaching`(異常扱い) / `ignore` から選択
- 複合アラーム(Composite Alarm): 複数アラームを AND/OR で組み合わせ、通知のノイズを抑える
- メトリクス数式(Metric Math): 複数メトリクスを計算して新たな指標を作成（例: エラー率 = エラー数 / リクエスト数）
- 異常検知(Anomaly Detection): 機械学習で通常範囲のバンドを学習し、固定しきい値なしで異常を検出

#### EC2 のアラームアクション

- 回復(recover): ハードウェア障害時に同一インスタンスを同じ ID・プライベート IP で別ホストに復旧する。`StatusCheckFailed_System` の監視と組み合わせる
- ステータスチェック: システムステータスチェック(AWS 側の問題)とインスタンスステータスチェック(OS/設定の問題)を区別して監視する

### CloudWatch Logs

- ロググループ / ログストリーム: ログの論理的な入れ物と、ソースごとのログの連なり
- サブスクリプションフィルター: ログをリアルタイムで Lambda、Kinesis Data Streams、Firehose、OpenSearch へ転送する
- メトリクスフィルター: ログ内の特定パターン(例: `ERROR` の件数)を数値メトリクス化し、アラームにつなげる
- 保持期間: ロググループごとに設定(デフォルトは無期限)。コスト最適化のため適切に設定する
- Logs Insights: 専用クエリ言語でログを対話的に検索・集計・可視化する
- Live Tail: ログをほぼリアルタイムで追跡表示する

#### メトリクスフィルターとサブスクリプションフィルターの違い

どちらも CloudWatch Logs のログに対してパターンを適用する機能だが、目的と出力先が異なる。

- メトリクスフィルター: ログ中の特定パターンの出現を数値メトリクス化する。出力先は CloudWatch メトリクスで、CloudWatch 内で完結する。例: ログ中の `ERROR` の件数をメトリクス化し、アラームで通知する
- サブスクリプションフィルター: ログイベント本文をリアルタイムで別サービスへ転送(ストリーミング)する。例: ログを Firehose 経由で S3 に集約、OpenSearch で検索、Lambda で加工する

| 項目 | メトリクスフィルター | サブスクリプションフィルター |
| ---- | -------------------- | ---------------------------- |
| 主目的 | ログを数値メトリクス化 | ログイベントを他サービスへ転送 |
| 出力 | CloudWatch メトリクス（数値） | ログイベント本文（リアルタイムストリーム） |
| 転送先 | なし（CloudWatch 内で完結） | Lambda / Kinesis Data Streams / Firehose / OpenSearch |
| 後続アクション | アラーム → SNS 通知や Auto Scaling | 加工・保存・検索・分析など自由 |
| 代表ユースケース | エラー件数を監視して通知 | ログの集約基盤・リアルタイム分析 |

一言でまとめると、メトリクスフィルターは「ログを数えてアラームにつなげる」、サブスクリプションフィルターは「ログ本文をそのまま流して別の場所で活用する」機能。

### CloudWatch Contributor Insights

ログやメトリクスを分析し、「最も寄与している要因(contributor)」をランキング表示する。トップ N の IP アドレスや URL など、負荷や異常の原因を特定するのに役立つ。

### CloudWatch Synthetics

Canary(スクリプト)を定期実行し、エンドポイントや API、ワークフローを外形監視する。ユーザー視点での可用性・レイテンシーを計測する。

### CloudWatch RUM / Evidently / ServiceLens

- RUM(Real-User Monitoring): 実ユーザーのブラウザからのパフォーマンスやエラーを収集する
- Evidently: フィーチャーフラグや A/B テストを安全に実施する
- ServiceLens: メトリクス・ログ・トレース(X-Ray)を統合し、サービス全体を可視化する

### クロスアカウント / クロスリージョンの可観測性

CloudWatch オブザーバビリティアクセスマネージャーを使うと、モニタリングアカウントから複数のソースアカウントのメトリクス・ログ・トレースを横断的に閲覧できる。

## Amazon EventBridge

AWS サービスやアプリケーションのイベントをルールでフィルタリングし、ターゲット（Lambda、SNS、Step Functions など）に配信するイベントバス。イベント駆動の自動修復に利用する。

## AWS CloudTrail

AWS アカウント内の API コールや管理アクションを記録・監査するサービス。「誰が・いつ・何をしたか」を追跡する。

| 種類 | 対象 | デフォルト記録 | 代表例 |
| ---- | ---- | -------------- | ------ |
| 管理イベント | 制御プレーン操作 | 有効 | EC2 作成/削除、IAM 操作 |
| データイベント | データプレーン操作 | 無効 | S3 オブジェクト操作、Lambda 呼び出し |
| インサイトイベント | 異常検知 | 無効 | API 呼び出し頻度の急増 |

## AWS Systems Manager

EC2 やオンプレを含むリソースの運用管理を一元化するサービス。試験頻出。

- Run Command: 複数インスタンスへのコマンド一括実行
- Patch Manager: OS パッチ適用の自動化
- Session Manager: SSH/RDP 不要のセキュアなシェルアクセス
- Parameter Store: 設定値やシークレットの一元管理
- State Manager: 設定を望ましい状態に維持
- Automation: 運用タスクのワークフロー自動化
- OpsCenter: 運用上の問題（OpsItem）を一元管理
- Distributor: ソフトウェアパッケージの作成・配布・インストール

### Systems Manager Distributor

ソフトウェアパッケージを作成・管理し、管理対象インスタンス群へ配布・インストールする機能。エージェントやソフトを「パッケージ」としてまとめ、EC2 やオンプレのマネージドインスタンスへ一括配布する。

- AWS 提供の事前定義パッケージ（CloudWatch Agent など）と独自パッケージの両方を扱える
- バージョン管理が可能で、配布するバージョンを指定できる
- 配布方法:
  - Run Command でオンデマンドに一括インストール
  - State Manager で「常に特定バージョンがインストールされている状態」を維持（新規インスタンスにも自動適用）
- Windows / Linux の複数プラットフォームやアーキテクチャ別のパッケージを定義できる

用途: 全インスタンスへ監視・セキュリティ系エージェントを標準配布しバージョンを統一したいとき、Auto Scaling で増えた新規インスタンスにも State Manager と組み合わせて自動的に同じソフトを入れたいとき。

| 機能 | 役割 |
| ---- | ---- |
| Distributor | ソフトウェアパッケージの作成・配布・インストール |
| Patch Manager | OS やアプリのパッチ適用の自動化 |
| Run Command | 任意のコマンドをインスタンスに一括実行 |
| State Manager | 望ましい状態（設定・ソフト）を継続的に維持 |

## Amazon Managed Grafana / CloudWatch への分析

CloudWatch メトリクスやログを可視化・分析し、パフォーマンスのボトルネックを特定する。Logs Insights や Contributor Insights で寄与度の高い要因を分析する。

# 分野 2: 信頼性と事業の継続性

高可用性、スケーラビリティ、バックアップ、ディザスタリカバリを実現するサービス群。

## Elastic Load Balancing (ELB)

トラフィックを複数のターゲットに分散し、可用性を高めるロードバランサー。

| 種類 | レイヤー | 主な用途 |
| ---- | ------- | -------- |
| Application Load Balancer (ALB) | L7 (HTTP/HTTPS) | パスベース・ホストベースのルーティング |
| Network Load Balancer (NLB) | L4 (TCP/UDP) | 超低遅延・高スループット |
| Gateway Load Balancer (GWLB) | L3 | ファイアウォールなどの仮想アプライアンス |

アクセスログはデフォルトで無効のため、必要に応じて有効化する。

## Amazon EC2 Auto Scaling

需要に応じて EC2 インスタンス数を自動で増減させる。希望/最小/最大キャパシティとスケーリングポリシーを設定する。

- ライフサイクルフック: スケールイン/アウト時に処理（ログ退避など）を挿入できる
- ヘルスチェック: 異常インスタンスを自動で置き換える

## EC2 プレイスメントグループ

EC2 インスタンスの物理的な配置方法を制御する仕組み。目的に応じて 3 種類から選ぶ。

- クラスター: インスタンスを単一 AZ 内で物理的に近接配置する。低レイテンシー・高スループットなネットワーク通信が目的。まとまって配置されるためラック障害の影響を受けやすい。用途は HPC、機械学習の学習など密結合なワークロード
- パーティション: インスタンスを複数のパーティション（最大 7 個/AZ）に分割配置する。各パーティションは独立したラック（電源・ネットワーク）を使うため、1 つのパーティション障害が他に波及しない。用途は Hadoop(HDFS)、Cassandra、Kafka などの大規模分散ワークロード
- スプレッド: 少数の重要インスタンスを 1 台ずつ別ハードウェアに分散配置する（7 インスタンス/AZ まで）。個々のインスタンスの障害分離が目的

| 項目 | クラスター | パーティション | スプレッド |
| ---- | ---------- | -------------- | ---------- |
| 配置方針 | 物理的に近接 | 独立ラックのグループに分割 | 個々を別ハードウェアに分散 |
| 主目的 | 低レイテンシー・高スループット | 障害分離 + 大規模分散 | 障害分離（少数の重要インスタンス） |
| 障害分離の単位 | なし（まとまって影響） | パーティション単位 | インスタンス単位 |
| 規模 | 中規模 | 大規模（最大 7 パーティション/AZ） | 小規模（7 インスタンス/AZ まで） |
| 代表用途 | HPC、ML 学習 | Hadoop、Cassandra、Kafka | 重要な個別サーバーの冗長化 |

一言でまとめると、クラスターは「くっつけて速くする」、パーティションは「ラック単位で分けて大規模分散の障害を局所化する」、スプレッドは「少数の重要インスタンスを 1 台ずつ別ハードに分ける」。

## Amazon Route 53

スケーラブルな DNS サービス。ルーティングポリシー（加重、レイテンシー、フェイルオーバー、位置情報など）とヘルスチェックで可用性を高める。DR 時のトラフィック切り替えに使用する。

## AWS Backup

複数の AWS サービス（EBS、RDS、DynamoDB、EFS など）のバックアップを一元管理するサービス。バックアップポリシーとスケジュールを集中管理する。

## Amazon S3

高耐久性(99.999999999%)のオブジェクトストレージ。バックアップ、静的コンテンツ、ログ保管などに利用。

- ストレージクラス: コストと取り出し速度のトレードオフで選択（詳細は下表）
- ライフサイクルポリシー: 自動的に別クラスへ移行・削除
- バージョニング / レプリケーション（CRR/SRR）: 誤削除対策とリージョン間冗長化

### ストレージクラス一覧

アクセス頻度・取り出しコスト・可用性のトレードオフで選択する。

- S3 Standard: 頻繁にアクセスするデータ向けの標準クラス。3 AZ 以上に冗長化、取り出し料金なし、最低保存期間なし
- S3 Intelligent-Tiering: アクセスパターンを自動モニタリングし最適な階層へ自動移動。取り出し料金なし（少額のモニタリング料金あり）。アクセス頻度が読めないデータに最適
- S3 Standard-IA（Infrequent Access）: アクセス頻度は低いが即時取り出しが必要なデータ向け。3 AZ 冗長化、取り出し料金あり、最低保存期間 30 日。バックアップや DR 用
- S3 One Zone-IA: Standard-IA と同様だが単一 AZ のみに保存（約 20% 安いが AZ 障害で消失の可能性）。再作成可能なデータ向け。最低保存期間 30 日
- S3 Glacier Instant Retrieval: アーカイブ用途ながら取り出しがミリ秒単位で即時。四半期に 1 回程度しかアクセスしないが即時性が必要なデータ向け。最低保存期間 90 日
- S3 Glacier Flexible Retrieval（旧 S3 Glacier）: 低コストのアーカイブ。取り出しは迅速(1〜5 分)/標準(3〜5 時間)/大容量(5〜12 時間)。最低保存期間 90 日。年数回アクセスするアーカイブ向け
- S3 Glacier Deep Archive: 最も安価な最長期保存クラス。取り出しに 12〜48 時間。最低保存期間 180 日。法規制対応の長期保管向け
- S3 Express One Zone: 単一 AZ の高性能クラス。一桁ミリ秒の超低遅延で Standard の最大 10 倍高速。レイテンシー重視のワークロード向け

| ストレージクラス | アクセス頻度 | AZ 数 | 取り出し速度 | 最低保存期間 | 主な用途 |
| ---------------- | ------------ | ----- | ------------ | ------------ | -------- |
| S3 Standard | 高頻度 | 3+ | 即時 | なし | 頻繁に使うデータ |
| S3 Intelligent-Tiering | 不定/変動 | 3+ | 即時（階層による） | なし | 予測困難なアクセス |
| S3 Standard-IA | 低頻度 | 3+ | 即時 | 30 日 | バックアップ、DR |
| S3 One Zone-IA | 低頻度 | 1 | 即時 | 30 日 | 再作成可能なデータ |
| S3 Glacier Instant Retrieval | アーカイブ（即時要） | 3+ | ミリ秒 | 90 日 | 即時取り出しアーカイブ |
| S3 Glacier Flexible Retrieval | アーカイブ | 3+ | 数分〜数時間 | 90 日 | 年数回のアーカイブ |
| S3 Glacier Deep Archive | 長期アーカイブ | 3+ | 12〜48 時間 | 180 日 | 長期保管、法規制対応 |
| S3 Express One Zone | 超高頻度・低遅延 | 1 | 即時（超低遅延） | なし | レイテンシー重視 |

選び方の目安は、アクセスパターンが読めないなら Intelligent-Tiering が無難。IA 系は取り出し料金と最低保存期間に注意。Glacier 系は取り出し時間とコストのトレードオフで選ぶ。One Zone 系は消えても再作成できるデータに限定する。

### Object Lock（ガバナンスモードとコンプライアンスモード）

S3 Object Lock はオブジェクトに WORM（Write Once Read Many: 一度書いたら変更・削除不可）を適用し、誤削除や改ざんから保護する仕組み。保持モードに 2 種類がある。

- ガバナンスモード: 原則として上書き・削除・保持短縮を防ぐが、特別な権限（`s3:BypassGovernanceRetention`）を持つユーザーは解除・上書きできる。社内ルールで保護しつつ管理者の例外対応を残したい場合に使う
- コンプライアンスモード: 保持期間中は誰も（ルートユーザーや AWS アカウント管理者を含めて）削除・上書き・保持短縮できない。保持期間の延長のみ可能。法規制(SEC 17a-4 など)で改ざん不可を証明する必要がある場合に使う

| 項目 | ガバナンスモード | コンプライアンスモード |
| ---- | ---------------- | ---------------------- |
| 保護の強さ | 中（例外あり） | 最強（例外なし） |
| 保持の解除・短縮 | 特別権限を持つユーザーは可能 | 誰も不可（ルートユーザーも不可） |
| 保持期間の延長 | 可能 | 可能 |
| バイパス | `s3:BypassGovernanceRetention` 権限で可能 | 不可 |
| 用途 | 社内ルールでの保護、例外運用を残したい | 法規制対応、絶対的な改ざん防止 |

保持の指定方法には、期間で保護する「保持期間(Retention Period)」と、期間を定めず明示的に解除するまで保護する「リーガルホールド(Legal Hold)」がある。リーガルホールドはモードとは独立して設定でき、`s3:PutObjectLegalHold` 権限が必要。

一言でまとめると、ガバナンスモードは「権限を持てば例外対応できる保護」、コンプライアンスモードは「誰も覆せない絶対的な保護」。

## Amazon RDS / Amazon Aurora

マネージドなリレーショナルデータベース。

- マルチ AZ 配置: 同期レプリカへ自動フェイルオーバーし高可用性を実現
- リードレプリカ: 読み取り負荷の分散
- 自動バックアップ / スナップショット: ポイントインタイムリカバリ
- Aurora グローバルデータベース: リージョン間 DR と低遅延リード

### Aurora Backtrack（バックトラック）

Aurora クラスターを、復元せずに過去の特定時点までその場で「巻き戻す」機能。誤った DELETE/UPDATE やテーブル削除の直後に、短時間で直前の状態へ戻せる。

- 変更レコードを一定の「バックトラックウィンドウ」（最大 72 時間）保持し、そのログで指定時刻へ戻す
- 巻き戻しは数秒〜数分で完了し、やり直し（前後への移動）も可能
- **Aurora MySQL 互換エディションのみ対応**（Aurora PostgreSQL は非対応）
- クラスター作成時に有効化が必要（既存クラスターへの後付け不可）
- 論理的なデータ破損からの迅速な復旧向け。ハードウェア障害対策ではない

| 項目 | Aurora Backtrack | ポイントインタイムリカバリ (PITR) |
| ---- | ---------------- | ------------------------------- |
| 方式 | 既存クラスターをその場で巻き戻す | バックアップから新しいクラスターを復元 |
| 速度 | 速い（数秒〜数分） | 遅い（新クラスター作成が必要） |
| 復元先 | 同じクラスター | 別の新規クラスター |
| 対象期間 | 最大 72 時間 | バックアップ保持期間内の任意時点 |
| やり直し | 可能（前後に移動） | 不可 |

## AWS Elastic Disaster Recovery / バックアップ戦略

RTO/RPO に応じて DR 戦略（バックアップ&リストア、パイロットライト、ウォームスタンバイ、マルチサイト）を選択する考え方が問われる。

# 分野 3: デプロイ、プロビジョニング、オートメーション

Infrastructure as Code(IaC)と自動デプロイのサービス群。

## AWS CloudFormation

テンプレート(JSON/YAML)でインフラをコード化しプロビジョニングする IaC サービス。試験頻出。

- スタック: テンプレートから作成されるリソースの集合
- StackSets: 複数アカウント・複数リージョンへ一括展開
- ドリフト検出: 実リソースとテンプレートの差分を検出
- 変更セット: 更新前に影響範囲をプレビュー
- DeletionPolicy / UpdatePolicy: 削除・更新時の挙動を制御
- cfn-init / ヘルパースクリプト: EC2 起動時の初期化

## AWS Elastic Beanstalk

アプリをアップロードするだけで、EC2・ELB・Auto Scaling などの環境を自動構築する PaaS。デプロイポリシー（All at once、Rolling、Immutable、Blue/Green）を選択する。

## AWS Systems Manager（オートメーション）

Automation ドキュメント(Runbook)で定型運用を自動化する。パッチ適用やインスタンス復旧などに利用。

## EC2 Image Builder

OS イメージ(AMI)やコンテナイメージのビルド・テスト・配布を自動化するサービス。ディストリビューション設定で配布先リージョンやアカウントを管理する。

## AWS OpsWorks

Chef / Puppet を使った構成管理サービス。（新規採用は非推奨傾向だが試験範囲として押さえる）

## AWS Lambda

サーバー管理不要でコードを実行するサーバーレスコンピュート。イベント駆動の自動化処理に多用する。

| 項目 | 予約済み同時実行 | プロビジョンドコンカレンシー |
| ---- | ---------------- | ---------------------------- |
| 目的 | 同時実行枠の確保・制御 | コールドスタートの解消 |
| コールドスタート | 解消できない | 解消できる |
| 課金 | 通常課金 | 環境維持に追加料金 |

# 分野 4: セキュリティとコンプライアンス

アクセス制御、暗号化、監査、脅威検知のサービス群。

## AWS IAM

ユーザー・グループ・ロール・ポリシーで AWS リソースへのアクセスを制御する。最小権限の原則が基本。

- IAM ロール: 一時認証情報を付与。EC2 インスタンスプロファイルやサービス間連携に使用
- IAM ポリシー: JSON で許可/拒否を定義

## AWS IAM Identity Center

複数アカウントとアプリへのシングルサインオン(SSO)を提供。Organizations と連携し、権限セットでアクセスを集中管理する。

## AWS Organizations

複数の AWS アカウントを一元管理する。

- 組織単位(OU): アカウントをグループ化
- SCP(サービスコントロールポリシー): アカウント/OU に対する権限のガードレール（上限）
- 委任管理者: 特定サービスの管理を他アカウントに委任

## AWS KMS

暗号化キーを管理するサービス。S3、EBS、RDS などの暗号化(保管時の暗号化)に使用。カスタマーマネージドキーの自動ローテーションが設定可能。

## AWS Config

リソースの構成変更を記録し、ルール(マネージド/カスタム)でコンプライアンス評価する。アグリゲーターで複数アカウント・リージョンのデータを集約する。

## AWS Secrets Manager / Parameter Store

認証情報や API キーなどのシークレットを安全に保管・ローテーションする。

## Amazon GuardDuty

ログ(VPC Flow Logs、CloudTrail、DNS Logs)を機械学習と脅威インテリジェンスで解析し、脅威を検知するサービス。

## Amazon Inspector

EC2 / ECR / Lambda の脆弱性(CVE)や設定不備を自動スキャンするサービス。

## AWS Security Hub

GuardDuty や Inspector などの検出結果を集約・標準化し、セキュリティ状態を一元管理する。

| サービス | 主な目的 | 対象 |
| -------- | -------- | ---- |
| GuardDuty | 脅威検知 | アカウント全体のログ |
| Inspector | 脆弱性管理 | EC2 / ECR / Lambda |
| Security Hub | 統合管理・可視化 | 各サービスの検出結果 |

## AWS WAF / AWS Shield

- WAF: Web アプリへの SQL インジェクションや XSS などをフィルタリング
- Shield: DDoS 攻撃からの保護(Standard は自動、Advanced は追加保護)

# 分野 5: ネットワークとコンテンツ配信

VPC、DNS、接続、コンテンツ配信のサービス群。

## Amazon VPC

論理的に分離された仮想ネットワーク。サブネット、ルートテーブル、インターネットゲートウェイ、NAT ゲートウェイなどを構成する。

- セキュリティグループ: インスタンス単位のステートフルなファイアウォール
- ネットワーク ACL: サブネット単位のステートレスなフィルタリング
- VPC Flow Logs: ネットワークトラフィックの記録。接続のトラブルシュートに使用
- VPC エンドポイント: AWS サービスへプライベート接続(Gateway/Interface 型)

## Amazon Route 53

DNS サービス。ドメイン登録、名前解決、各種ルーティングポリシー、ヘルスチェックを提供。Resolver でハイブリッド環境の DNS 解決も行う。

## Amazon CloudFront

エッジロケーションからコンテンツを配信する CDN。キャッシュによる低遅延配信と、オリジン保護(OAC)を提供する。

## AWS Direct Connect / Site-to-Site VPN

オンプレミスと AWS を接続するハイブリッド接続。

- Direct Connect: 専用線による安定・低遅延接続
- Site-to-Site VPN: インターネット経由の IPsec 暗号化トンネル

## AWS Transit Gateway

複数の VPC とオンプレミスネットワークをハブ&スポーク型で相互接続する。マルチ VPC 環境の接続を簡素化する。

## AWS Global Accelerator

AWS のグローバルネットワークを使い、エンドユーザーからアプリへの経路を最適化して可用性と性能を高める。

# コスト最適化（クラウド財務管理）

いずれも 1 年または 3 年の利用コミットでオンデマンドより割引を受ける仕組み。柔軟性と割引率がトレードオフになる。

## コンバーティブルリザーブドインスタンス (Convertible RI)

- 1 年または 3 年のコミットで割引（オンデマンド比で最大 54% 程度）
- 期間中にインスタンスファミリー・OS・テナンシー・リージョンを変更（交換）できるのが特徴。変更不可で割引率が高い「スタンダード RI」と対比される
- ゾーン指定の RI は特定 AZ のキャパシティを確保できる（リージョン RI は確保なし）

## Compute Savings Plans

- 1 年または 3 年の「時間あたり利用額（USD/時間）」のコミットで割引（最大 66% 程度）
- 最も柔軟で、EC2 だけでなく Lambda や Fargate にも適用される
- インスタンスファミリー・サイズ・AZ・リージョン・OS・テナンシーを問わず自動適用。キャパシティ予約の機能はない

## EC2 Instance Savings Plans

- 1 年または 3 年の利用額コミットで割引（最大 72% 程度と Compute より高い）
- 特定リージョンの特定インスタンスファミリーの利用にコミットする
- そのファミリー内であればサイズ・AZ・OS・テナンシーの変更には柔軟に追従する。対象は EC2 のみ

## 比較表

| 項目 | Convertible RI | Compute Savings Plans | EC2 Instance Savings Plans |
| ---- | -------------- | --------------------- | -------------------------- |
| コミット対象 | 特定条件のインスタンス | 時間あたり利用額（$/h） | 時間あたり利用額（$/h）＋特定ファミリー |
| 割引率（目安） | 最大 54% | 最大 66% | 最大 72% |
| 対象サービス | EC2（他サービスにも RI あり） | EC2 / Lambda / Fargate | EC2 のみ |
| 柔軟性 | ファミリー等を交換可能 | 非常に高い（横断的に自動適用） | 同一ファミリー内で柔軟 |
| ファミリー変更 | 交換で可能 | 自由 | 不可（ファミリーに固定） |
| キャパシティ予約 | ゾーン RI なら可能 | なし | なし |
| 向いているケース | 割引を使いつつ構成変更に備えたい | 構成が頻繁に変わる・サーバーレス併用 | 使うファミリーが決まっていて割引を最大化したい |

選び方の目安は、構成が変わりやすい・Lambda/Fargate も使うなら Compute Savings Plans、使うファミリーが固まっていて割引を最大化したいなら EC2 Instance Savings Plans、キャパシティ予約も欲しい・RI 運用を続けたいなら Convertible RI。

# 学習のポイント

- 運用系の分野 1〜3 で全体の 2/3 を占めるため、CloudWatch / Systems Manager / CloudFormation / Auto Scaling は重点的に学習する
- AWS マネジメントコンソールだけでなく AWS CLI での操作も問われる
- 高可用性・DR の設計パターン(RTO/RPO)と各サービスの可用性オプションを整理する
- トラブルシューティング(ネットワーク疎通、権限不足、デプロイ失敗など)の原因切り分けを問う設問が多い
