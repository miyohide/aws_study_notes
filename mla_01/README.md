- 目的：データの視覚化、クレンジング、変換

- 目的：ビジュアルデータ準備ツール。データのクリーニングと正規化をGUI操作（ノーコード）で実装できる
- 参考：[AWS Glue DataBrew](https://aws.amazon.com/jp/glue/features/databrew/)

#### AWS Glue Studio

- 目的：ETLジョブの作成・実行をGUIで組み立てられる

## 推論エンドポイント

### マルチモデルエンドポイント（MME）と マルチコンテナエンドポイント（MCE）の違い

1つのエンドポイントで複数のモデルを提供する仕組みだが、目的が異なる。

| 項目 | マルチモデルエンドポイント（MME） | マルチコンテナエンドポイント（MCE） |
| --- | --- | --- |
| 目的 | 同じフレームワーク・コンテナで、多数のモデルを効率よくホストする | 異なるフレームワーク・コンテナのモデルを1つのエンドポイントにまとめる |
| コンテナ | 1種類のコンテナを共有 | 最大15個の異なるコンテナ |
| モデルの数 | 数千規模まで可能 | コンテナ数に依存（最大15） |
| モデルの読み込み | 呼び出し時にS3から動的にロード（使わないモデルはメモリから退避） | 各コンテナは常時ロード済み |
| 呼び出し方法 | リクエストで対象モデルを指定 | リクエストで対象コンテナを指定、または直列に連結（推論パイプライン）できる |
| 向いているケース | 同種のモデルが大量にあり、コストを抑えたい | 異なる種類のモデルを1つのエンドポイントに集約したい |

- MME：多数の類似モデルを低コストで運用したいとき。使用頻度の低いモデルはメモリから退避されるため、リソースを節約できる。
- MCE：フレームワークが異なるモデル（例：TensorFlowとPyTorch）を同居させたいときや、複数モデルを直列でつなぐ推論パイプラインを組みたいとき。

## ハイパーパラメータチューニング

| 戦略                        | 探索方法                | 過去の試行結果を利用 |  並列実行 | 特徴                     | 向いているケース           |
| ------------------------- | ------------------- | ---------: | ----: | ---------------------- | ------------------ |
| **Grid Search**           | 全組み合わせを網羅           |          ❌ |     ○ | 指定したカテゴリ値の全組み合わせを試す    | 組み合わせが少ない、再現性重視    |
| **Random Search**         | ランダムに選択             |          ❌ | **◎** | 各試行が独立しているので大量並列実行しやすい | 試行回数を増やしたい、大規模探索   |
| **Bayesian Optimization** | 過去の結果から「良さそうな場所」を予測 |      **○** |     △ | 過去の結果を利用して次の候補を賢く選ぶ    | 学習コストが高く、効率的に探索したい |
| **Hyperband**             | 成績の悪い試行を早期終了        |          ○ | **◎** | 有望なモデルに計算リソースを集中       | 学習に時間がかかるモデル       |

### ベイズ最適化（Bayesian Optimization）

過去の試行結果をもとに「次に試すと良さそうなハイパーパラメータ」を推測しながら探索する手法。Grid Search や Random Search のように闇雲に試すのではなく、少ない試行回数で良い組み合わせにたどり着くことを狙う。

- 仕組み
  1. これまでの試行結果（ハイパーパラメータと精度の組み合わせ）から、精度を予測する代理モデル（サロゲートモデル、ガウス過程など）を作る
  2. 「良い精度が期待できそうな場所」と「まだ試していない未知の場所」のバランスを取りながら、次に試す候補を選ぶ（獲得関数を利用）
  3. 実際に学習して結果を得たら、その結果を代理モデルに反映して1に戻る
- 特徴
  - 過去の結果を活用するため、試行回数が少なくて済みやすい
  - 前の結果に依存するため、Random Search ほど大量の並列実行には向かない
- 向いているケース
  - 1回の学習コストが高く、試行回数をできるだけ抑えたいとき
  - SageMaker の自動モデルチューニング（AMT）でもデフォルトの戦略として利用できる

## データ前処理

### One-hot encoding

機械学習で扱いにくいカテゴリデータを、0と1の数値に変換する方法。例えば曜日というカテゴリデータを、カテゴリごとに列を作る。以下のような感じ。

| 曜日 | 月 | 火 | 水 |
| --- | --- | --- | --- |
| 月曜日 | 1 | 0 | 0 |
| 火曜日 | 0 | 1 | 0 |
| 水曜日 | 0 | 0 | 1 |

## 学習のテクニック

### 深層学習モデルの学習を安定させたい

学習率を小さく、ミニバッチを大きくする。

### 正則化（L1正則化・L2正則化）

過学習を抑えるために、損失関数へ重みの大きさに応じたペナルティ項を加える手法。ペナルティの計算方法によってL1とL2に分かれる。

| 項目 | L1正則化（Lasso） | L2正則化（Ridge） |
| --- | --- | --- |
| ペナルティ | 重みの絶対値の合計 | 重みの二乗の合計 |
| 重みへの影響 | 不要な重みを完全に0にする（スパースになる） | 重みを全体的に小さくする（0にはなりにくい） |
| 効果 | 特徴量の選択（自動的に重要な特徴だけ残す） | 重みの偏りを抑えて過学習を防ぐ |
| 適用ケース | 特徴量が多く、重要なものだけに絞りたいとき | 多くの特徴量をまんべんなく使いたい、多重共線性を抑えたいとき |

- L1正則化：不要な特徴量の重みが0になるため、実質的に特徴量選択として使える。特徴量が非常に多いケースに向く。
- L2正則化：すべての重みを均等に小さく抑える。特徴量間の相関（多重共線性）が強い場合に安定しやすい。
- 両方を組み合わせた手法として Elastic Net がある。

## 公平性・バイアスの指標

### DLP（ラベルの比率の差）

予測されたラベルの割合の差を測る、公平性を評価するための指標。異なるグループ間で、ポジティブな予測が出る割合にどれくらい差があるかを表す。

# 分類／回帰

- 分類は、データが属するクラスを予測する。
- 回帰は、連続する数値から今後の数値の変化を予測する。

# 学習率

パラメータ（重みやバイアス）をどれぐらい変化させるかを表すハイパーパラメータ。

- 学習率の値が大きすぎると学習のスピードは上がるが最適解に収束しない（振動する or 発散する）
- 学習率の値が小さすぎると収束しやすいが、収束までに時間がかかる

# オーバーフィッティングとその対処

学習データに対して絵記号しすぎてしまい、未知のデータに対しては期待する精度が出ない状態になること。対処方法として、以下のことを実施する。

- 正則化の制約を増やす
- ドロップアウトを増やす
- 次元圧縮
- レイヤーを減らして単純なモデルにする
- 学習率を小さくする

# 歪んだデータへの対処方法

- 対数変換
- ビニング
    - 1つの特徴量を一定間隔に分割して、それぞれの区間を違う特徴量とみなして重回帰をする

# 混合行列

| - | 実データ・正 | 実データ・負 |
| --------- | ------------- | -------------- |
| 予測・正 | 真陽性（TP） | 偽陽性（FP） |
| 予測・負 | 偽陰性（FN） | 真陰性（TN） |

正や負がそれぞれ正解／不正解を常に表現しているとは限らないことに注意。モデルにより検出したいほうを陽性と表現することが多い。

評価指標として、以下のものを認識しておく

- リコール（再現性、真陽性率）= TP / (TP + FN)
    - 実際に陽性のデータのうち、どれだけ正しく陽性と判定されたか
    - 病気検出やスパム検出など **検出漏れを減らす** 場合に活用
- 適合率（精度） = TP/(TP + FP)
    - 陽性と予測した中で、本当に陽性の割合
    - 詐欺検出など **誤検知を減らす** 場合に活用

リコールと適合率の調和平均を表すF1値を活用することが多い（リコールと精度はトレードオフになるため）

# オーバーサンプリング／アンダーサンプリング

- オーバーサンプリングは、件数が少ないデータを増やすこと
    - 手法の一つにSMOTE（Synthetic Minority Over-sampling TEchnique）がある。k-NNアルゴリズムを用いる
- アンダーサンプリングは、件数が多いデータを減らすこと
